# 3.12.13 — opt-in Winter Crisis Director

This is a bounded coordinator over WorldState/conditions, not a second story engine.
It is OFF for every save without an explicit operator enable command. There are no
automatic crisis registrations or triggers. The only supplied scenario is a manual,
diagnostic technical test. It does not change weather, blocks, power, fuel, batteries,
story variables, objectives, dialogues, music or existing save formats.

## Components and lifecycle

* `WinterCrisisDirector`: deterministic coordinator, immutable Spec/Target/View/Event,
  IDs and UUIDs only, bounded transient instances, explicit action boundary.
* `CrisisRuntime`: server lifecycle, permission-2 commands, scoped observations and
  diagnostic-only action adapter. Registered once from PowerDevices.
* `CrisisSettings`: separate version-1 settings file, no active-session persistence.
* Stage 5 supplies `WinterCrisisConditions` and `CrisisWorldSource`.

Specs include ID, player/group/world target, precondition and trigger, priority,
maximum runs, hold/arm/duration/cooldown ticks and explicit cancellation/completion
policies. Current policies require TRUE while active and complete after a duration.
Targets hold an expected dimension and at most 8 player UUIDs; WORLD holds none.
All API calls are owned by the server thread. No asynchronous scheduler is used.

Transitions: registration -> IDLE; manual arm -> ARMED; held TRUE -> ACTIVE;
duration -> COMPLETED; a recoverable repeat slot -> COOLDOWN -> IDLE. New activation
always requires another manual request. ARMED/ACTIVE may become CANCELLED; terminal
states remain visible. Cancelled attempts that did not enter ACTIVE do not consume a
run, but still cool down. Successful/partially failed entry consumes a run. Exhausted
instances remain terminal until operator reset. Reset intentionally clears temporary
limits, not story progress. No retry loop or automatic re-arming exists.

UNKNOWN never activates. While ACTIVE, FALSE or UNKNOWN cancels. Disconnect cancels
affected player/group instances immediately; expected-dimension changes and missing
worlds are checked on the next scheduled evaluation. Last logout cancels pending
and active work. Missing/unloaded/removed devices or networks become UNKNOWN through
WorldState. Stop closes the director, cancels work once and drops references. An
exception in presence, sampling or actions is contained to the scenario. Failed
cancellation is reported in its status and is not retried.

## Operator commands

All are under `/whiteout crisis` and require permission level 2.

| Command | Effect |
| --- | --- |
| `status` | Enabled/config-blocked flags, up to 16 instance statuses, last 6 transitions |
| `enable` | Save enabled=true for this world save, then enable runtime |
| `disable` | Cancel first, disable runtime, then save enabled=false |
| `test [network]` | Player-only manual technical test; optional exact network ID |
| `cancel` | Cancel all ARMED/ACTIVE technical tests |
| `reset` | Clear all transient instances, repeat limits and diagnostic history |

The test uses known weather and shelter facts. Each probe is X OR NOT X: this is
TRUE for either known value, but UNKNOWN for unavailable data. An optional network
adds a known-network probe. This deliberately tests availability without requiring
a blizzard/outage or causing one. It holds for 10 ticks, arms for at most 200 ticks,
runs for 40 ticks, cools down for 100 ticks and permits 3 entries per registered
player test. Sampling can delay state transitions. ACTIVE/completion/cancellation
write diagnostic log entries and the bounded runtime history only.

One instance per player ID prevents duplicates. Repeat with `test` without an
argument after cooldown; it retains its original probes. To change the dimension
or optional network, use reset first. Up to 16 player test slots remain until reset
or server stop. No broadcast, arbitrary command execution or GUI is introduced.

## Existing Director / story integration boundary

The actual binary base and current sources were inspected:
`client.director.DirectorTriggerManager` checks `StoryRules.matches` and invokes
`StoryRuntime.fire` / `DirectorPlayer.play`. `DirectorPlayer` opens dialogues through
`DialogueManager.open` / `openDirector`. Overlay `power.DialogueTriggers` also calls
the client DialogueManager. Server `director.DirectorActors.begin` calls `stopAll`
before creating a session. Calling it for a new crisis would interrupt an existing
director session; it is not a safe independent scene-launch API.

Therefore the server runtime imports none of those client classes and does not
patch their binary implementations or reproduce story variables/objectives/events.
`WinterCrisisDirector.Actions.enter/complete/cancel` is the explicit integration
boundary. The shipped adapter only logs. A future trusted adapter must negotiate
scene ownership, use existing StoryRuntime/StoryRules APIs and an authenticated
server/client launch protocol, and handle partial failure/cancellation. Persistent
one-shot story actions need their existing durable completion protocol before they
can be enabled here. Configuration does not accept executable actions or scripts.

To add scenarios later, construct validated Specs in trusted server code, register
them with the coordinator and explicitly arm them. Add only the required adapter
capability rather than a parallel story store. Automatic triggers/editor/content
are intentionally outside this version.

## Persistence and safety

`<world-save>/whiteout-winter-crisis.json` contains exactly
`{"version":1,"enabled":false}` (or true). Missing file means disabled and does not
create a file. Only an explicit enable/disable writes it. Existing Whiteout stores
and NBT are untouched: no migration is needed.

Read bound: 4096 bytes. Invalid/unknown schema disables the runtime and blocks
writes, preserving the original bytes. Repair this separate file externally and
restart; the runtime never silently substitutes defaults on disk. Before a write,
an existing file is revalidated. Writes use a unique sibling temporary file,
re-read validation, atomic replace when supported, normal replace as the documented
fallback, and cleanup. A write failure is reported to the operator. Disable still
stops runtime immediately if persistence fails; an old enabled flag can consequently
remain on disk, so resolve the reported failure before restart.

Only the enabled flag survives restart. No instances, active state, repeat counters,
cooldowns, callbacks or action queues are restored; even an enabled save starts
with zero scenarios. Thus nothing replays on load. Temporary repeat limits reset
after restart; this is safe for the diagnostic scenario, not yet a durable policy
for future story-changing actions.

## Performance

Disabled: lifecycle bookkeeping only; no condition source, actions or world scans.
Enabled: scheduler once per 10 server ticks, at most 4 instance evaluations per
cycle, 16 registered instances, 4 ACTIVE, 64 diagnostic transitions (reason <=160
characters). Oldest-checked instances are served first, priority then ID breaks
ties; this bounds starvation without preempting an active scenario. At full capacity
each eligible instance is checked within 40 ticks. Holds tolerate a 50-tick sample
gap. The shared per-cycle condition budget is 64 work units, with the stage-5 depth,
node and sampling bounds. Up to 8 members are resolved per target check. Sources
live for one cycle only; the server map is removed at stop. No chunk tickets,
chunk-load callbacks, full player/network scans or new network packets are added.

## Executed verification and remaining game checks

`compileJava check foundationTests` is the validation command, not a release build.
The suite includes existing regressions, 3276 actual Fabric-transformed barricade
collision checks, 114 support checks, WorldState cache/snapshot/lifecycle and 12
device NBT checks, 72 condition checks, 76 coordinator checks, 28 settings checks.
Coordinator cases cover lifecycle, manual cancel/repeat/duplicate, player/network
isolation, priority/capacity/cooldown, restart, unknown/error/missing sources,
disable/stop, failures in entry/completion/cancellation, bounds and reset. Settings
tests use disposable directories, invalid formats, externally corrupted data and
I/O failure; no user world is opened. Fabric SERVER bootstrap additionally loads
and registers CrisisRuntime twice. This checks class loading/registration, not an
actual dedicated-server world or all original mod entrypoints.

Required game pass: integrated and dedicated server with a future assembled JAR;
operator/non-operator commands; two players, disconnect/dimension change/last logout;
real chunk unload/reload and removed/renamed networks/devices; rapid zone switching;
disable during ACTIVE; stop/restart enabled world; old-map story/dialogue progress;
frame/tick cost and Iris/BSL visuals. No live play session or final-JAR test is claimed.
Release JAR, personal music, logs and caches are not added to Git.
