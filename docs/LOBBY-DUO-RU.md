# WHITEOUT — доска и совместная история

## Для игроков

На клиенте и сервере нужны одинаковый JAR WHITEOUT, Minecraft 1.21.1, Fabric Loader и Fabric API. Для тестовой карты выдайте предмет командой `/give @s whiteout:story_board`. Поставьте его на вертикальную стену с площадью 2×2 полных блоков и свободным пространством перед ней. Нажатие правой кнопкой по любой четверти открывает доску. Карточка и прохождение принадлежат миру. Другая установленная доска открывает ту же историю.

Оператор в творческом режиме открывает шестерёнку, заполняет название и сохраняет карточку. Остальные поля можно пропустить. В галерее можно импортировать PNG или JPG, перемещать кадр мышью, менять увеличение и расположение снимка, назначать главный снимок и заменять его из исходного файла. Сервер раздаёт готовые фотографии при открытии доски. В резервную копию мира включайте папку `whiteout-board-photos`.

В «Участниках» ведущий выбирает подключённого игрока. Приглашённый подходит к доске и принимает приглашение. Оба нажимают «Я готов», затем ведущий запускает историю на главной странице. После изменения общей конфигурации подтвердите готовность ещё раз. Для Solo достаточно запустить настроенную карточку без приглашённого партнёра.

Ведущий выбирает общую сложность. В ручном режиме доступны расход обоих генераторов, время работы лампы, зарядки и работы фонаря, вероятность и интервал отказа предохранителя, время охлаждения в метель и снег. Личные настройки чтения, портретов, подсказок и звука находятся отдельно у каждого игрока.

После выхода партнёра сюжет ждёт. Оставшийся участник может нажать сообщение в чате или ввести `/whiteout lobby continue-alone`. После возвращения партнёра снова действуют правила Duo. Персонажи привязаны к UUID. Выбор, доступный только отсутствующему персонажу, ждёт его возвращения.

## Для автора карты

В настройке старта укажите измерение и координаты либо оставьте игроков на месте. При желании укажите идентификатор существующего серверного одноразового события. Его область должна содержать точку прибытия. Для кат-сцен используйте файлы Director, доступные обоим клиентам. Для реплик подготовьте одноимённые диалоги штатным редактором WHITEOUT.

Редактор событий на доске читает и сохраняет каталог мира `whiteout-story-events.json`. Создайте событие или загрузите его по ID. Кнопки переключают режим, исполнителя, получателя и видимость. В текстовой области доступны точные условия, действия, переходы диалога и события Director. Сохранение проверяет весь каталог. Перед обновлением существующего файла создаётся копия с расширением `.bak`.

| Настройка | Что она определяет |
|---|---|
| `mode` | BOTH, SOLO или DUO |
| `actor` | Кто может инициировать событие. ANY, FIRST или SECOND |
| `recipient` | В чьём профиле сохранить результат действия |
| `visibility` | SHARED для общего события, PERSONAL для личного, SECRET для секретного |
| `scope` | WORLD для общей истории, PLAYER для личного прогресса |
| `when` | Условия по переменным или завершённым событиям мира, первого или второго персонажа |
| `together` | Все участвующие игроки должны находиться в области события |
| `firstDialogue`, `secondDialogue` | Дополнительные диалоги по ролям |
| `waitForReaders` | Дальнейшие события ждут, пока участники дочитают |
| `voteGroup` | Для общей развилки укажите одну группу на вариантах. Пройдёт вариант, который выбрали оба |
| `sharedScene` | ID камеры Director, длительность в тиках, серверное событие завершения |
| `endings` | Кандидаты с разными приоритетами. Побеждает подходящий с максимальным приоритетом |

**Секретная задача.** Выберите шаблон «Секретное», назначьте одного персонажа одновременно исполнителем и получателем. Добавьте в `objectives` действие START и определение цели с уникальным ID и названием. Для завершения создайте отдельное событие с действием COMPLETE для той же цели. Если предмет должен подобрать любой игрок для указанного персонажа, используйте PERSONAL, `actor: ANY`, конкретного получателя и `scope: PLAYER`. Для выбора в диалоге укажите точный ключ `dialogue_choice:<диалог>:<узел>:<вариант>` существующего диалога и добавьте его в `nextChoices` предыдущего разрешённого события.

**Финал.** Сначала создайте обычные серверные события WORLD с `once: true`, `serverOnly: true`, областью, условиями и действиями. Затем привяжите их к вариантам финального выбора. Для каждой ветки можно определить собственную `finale` с камерой Director и отдельным `completion`. Поле `deliveries` у концовки выдаёт результат сразу, а в описании сцены — при её завершении или согласованном пропуске. Для предмета укажите `recipient`, `item` и `count`, для перемещения задайте `move` с измерением и координатами. Награда ожидает входа получателя и свободного места в инвентаре.

В [примере трёх концовок](examples/duo-final-events.json) персонаж №2 может узнать о письме. В финале выбор выстрела включает камеру `final_loss`. Пощада включает `final_mercy`, а у прочитавшего письмо персонажа — `final_letter`. Игрок №1 получает собственный диалог. Это пример каталога для отдельного тестового мира. Подставьте координаты карты, реальные диалоги, узлы и длительности своих камер. При переносе в существующую карту объединяйте события с её каталогом.

## Сохранение и проверка

Общее состояние, профили персонажей, факт старта, выбранный финал, ожидающие награды и курсор общей сцены сохраняются в Store. Курсор записывается каждые 100 тиков. Голоса и готовность привязаны к текущему соединению. Защищённая команда `/whiteout lobby reset-launch confirm` открывает настройки запуска и сохраняет уже пройденные события. Для повторного тестирования всех финалов используйте копию мира, сделанную перед развилкой.

Основные расширения существующего кода находятся в StoryAuthority, StoryEventCatalog, TriggerAuthority, ScopedStory, Store и точках обработки диалогов, Director, генераторов и аккумулятора. За новые функции отвечают BoardBlock, BoardNetwork, LobbyState, Party, PhotoTransfer, Balance, StoryAuthor, Narrative, DialogueBarrier, SharedScene и SceneDelivery. У доски есть собственные модели, текстуры и перевод. Серверная логика не требует графического клиента.

Автопроверки проверяют раздельные профили и Once, выбор ветки по секретному прогрессу, миграцию старого Store, откат неудачной записи, восстановление курсора и ожидающих наград, сборку фотографий по частям и сохранение четырёх частей доски при перезапуске выделенного сервера. Визуальное кадрирование, читаемость на конкретном масштабе GUI и прохождение каждой ветки двумя реальными клиентами требуют игровой проверки.
